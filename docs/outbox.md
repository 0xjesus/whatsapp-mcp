# Durable outbound messages

`send_message`, `send_file`, `send_audio_message`, and `send_reply` persist an authorized message before attempting delivery. The response is `{Success, Accepted, Status, JobID, Message, ID}`. `Accepted: true` means the daemon owns the job. `Success: true` and `ID` confirm delivery. A queued result is not a delivery receipt.

Pass an optional `idempotency_key` to reuse an authorization safely when a request response is lost. An identical normalized recipient, message, options, and media snapshot returns the original job. Reusing a key for different content or a different paired sender is rejected. Without a key, each submission is a separate authorization. Do not repeat an accepted message.

Use `get_outbox` with `job_id` to inspect delivery, including its stable `message_id`. With no ID it lists up to 100 recent jobs. Status queries load metadata only. `cancel_outbox` cancels queued or blocked jobs; it refuses cancellation once delivery is in progress, uncertain (`needs_review`), or terminal. Uncertain jobs retain their stable IDs, snapshots, and original diagnostics. `get_status` includes queue counts, the next queued job, its next attempt time, and account health.

The daemon processes queued jobs in order. Local pacing and definite temporary server refusals retain the job until its next permitted attempt. SQLite protects all message sends across restart with floors of 45 seconds and 30 attempts per rolling hour. Recipients without inbound history use 90 seconds and 15 attempts per rolling hour. Features such as polls, reactions, edits, revocations, votes, and contact cards share the same dispatch mutex, account gate, and budget. Each reservation also updates the legacy ledger transactionally, preserving configured memory-limit restoration and rollback history without summing the two ledgers. Configuration may make limits stricter. A header cannot bypass message-send protection.

The same reservation also caps automated sends at 120 attempts in a rolling 24-hour window, 20 attempts per normalized recipient, and 20 distinct recipients without inbound history. Repeated attempts to one new recipient occupy one distinct-recipient slot while consuming the overall and recipient attempt quotas. These are local operator policies, not published WhatsApp quotas or a guarantee against restrictions. The daily ledger survives restarts and counts attempts before transport, including refused or uncertain deliveries. An exhausted quota leaves an outbox job queued until capacity becomes available.

Upgraded ledger rows without recipient identity still count toward the overall quota and conservatively toward each identified recipient's quota. Each such row without inbound history occupies one unknown-recipient slot. The old daemon retained only an hour of reservations, so the first daily window includes only retained pre-upgrade activity and new reservations. The daemon does not infer missing attempts from message history. It preserves the existing hourly budget and migration guard.

The native `NotifyAccountReachoutTimelock` event records a separate persistent restriction. An active signal conservatively pauses all automated recipient sends. A server-provided expiry or a newer inactive signal releases that condition, while another active ban, revoked session, circuit breaker or refusal cooldown continues to block. Reconnecting and successful-send bookkeeping do not erase it. A signal without an expiry keeps authorized jobs queued for local safety checks until a valid release arrives; those checks do not send messages or consume delivery attempts. Temporary restriction waits resume through the existing worker, preserving FIFO, stable IDs and send spacing.

The first migration atomically imports the existing `send_budget` ledger, preserves its hourly counts, and applies a one-time 90-second cushion for reservations that preceded typing. A database that lacked a legacy ledger before schema migration, including a fresh database, uses a full-hour fallback. Restart does not renew or remove this guard. Account health is persisted as well. A disconnected transport waits for reconnection. Each job is bound to the normalized paired sender; changing accounts blocks old authorization. Unpaired submissions are rejected.

An actual delivery attempt has a stable WhatsApp message ID. A definite typed IQ refusal or the pinned Whatsmeow `ErrServerReturnedError` acknowledgement wrapper with a strictly parsed 429, 463, or 475 code can retry after the full account cooldown, with increasing cooldowns and at most three delivery attempts. Unknown network outcomes enter `needs_review` and are never automatically retried. Bans, revoked sessions, sender changes, and exhausted attempts remain visible as blocked jobs. The operator must inspect the stable ID and outgoing history before authorizing a new send.

On startup, an interrupted `sending` job becomes `sent` only if the outgoing cache already contains its stable ID, outgoing flag, and recipient (including its recorded LID-to-phone mapping). Otherwise it becomes `needs_review`. The outgoing history is written before the terminal job update. A delivered message whose cache write fails still remains `sent` with an explanatory reason.

Media is snapshotted into SQLite when authorized, with a 64 MiB limit. Preparation/upload has a 90-second timeout; offline, cancellation, and transient upload failures retain the job for a later preparation attempt without consuming a recipient-delivery attempt. Permanent malformed media fails before upload, and account bans block preparation. Unknown recipient-delivery outcomes are never treated as preparation failures. Delivery never rereads the original file. Pending files can therefore be removed after acceptance. Voice notes fingerprint the original allowlisted source bytes, normalized recipient/options, and fixed conversion policy. Conversion uses a private immutable source snapshot; retries reuse the first persisted converted bytes even when FFmpeg assigns a different Ogg stream serial. Conversion artifacts never bypass or widen the public file allowlist. The `mark_chat_read` option is retained in the job and applied only after confirmed delivery.

The application serialization and persistent pacing promise covers recipient chat messages. History sync and view-once phone recovery are peer protocol traffic: the pinned dependency serializes them with its transport message lock, but they are outside the application recipient-message budget. View-once recovery has its existing health gate and cooldown; history sync has no equivalent application budget.

The worker starts only in `serve`; login and smoke commands do not drain old jobs. Shutdown waits for delivery bookkeeping. Scheduled text remains owned by the existing durable scheduler. Its synchronous dispatcher shares the outbox mutex, account health, and persistent budget; it never creates a second outbox authorization. Both queues retain their own cancellation and listing tools. New schedules bind to the paired sender; pre-upgrade pending schedules bind to the current sender once at serve startup, and sender changes thereafter stop dispatch. Scheduled transmissions persist stable IDs, recover confirmed outgoing cache entries, and stop after ambiguous delivery or bounded definite refusals. Exhausted scheduled jobs become visible terminal failures.
